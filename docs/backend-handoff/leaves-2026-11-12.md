# Leaves: giving leave to a new employee (12 Nov 2026)

For the backend developer. The question was: "I added a new employee. Where do I give them
leave?" The API could already do it all; the screens hid or lacked the way in. Part 1 is the one
backend change (already made in `hRango-Backend`). Part 2 is what the screens now call. Part 3 is
how leave reaches a person, for reference.

---

## 1. Backend change (done)

### L1. A company-level policy's "Enroll Employee" count was too high

`db/procedures/lv/usp_leave_policy.sql`, `lv.fn_leave_policy_rows`: a company-level policy
counted every employee who has not left, including people enrolled in an active employee-level
policy of the same kind. Those people are not covered by the company policy
(`lv.fn_leave_coverage` gives them their employee-level policy), so the table showed them twice
(for example 27 under the company policy and 5 under an employee-level one, with 27 people in
the company).

Now it counts only the people it really covers. Test: `tests/test_leaves_settings.py`,
`test_policies_and_enrolment` (the count drops by two after enrolling two people elsewhere).

No other backend change is needed.

## 2. Endpoints the screens now call

All existed already.

| Screen                                                                  | Call                                                                                                                                                       | Permission                                    |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| Leave Policies → **Enroll** button (employee-level policies)            | `GET/POST /leaves/policies/{id}/employees`, `DELETE /leaves/policies/{id}/employees/{employeeId}`                                                          | `leaves.settings.policies.enroll`             |
| Enroll Employee → "Give the people added their leave for this year now" | `GET /leaves/balances?employeeId=&pageSize=1` (for the leave year), then `POST /leaves/allotment/process { fiscalYear, employeeId }` per person added      | `leaves.allotment.process`                    |
| Allotment dialog → new **Employee** field (blank = everyone)            | `POST /leaves/allotment/process { fiscalYear, leaveTypeId, employeeId }`, `POST /leaves/carry-forward/process { fromFiscalYear, leaveTypeId, employeeId }` | `leaves.allotment.process`                    |
| Talent Management → employee → Leave tab → **Allot Leave**              | `POST /leaves/allotment/process { fiscalYear, employeeId }`                                                                                                | `leaves.allotment.process` (on that employee) |
| Talent Management → employee → Leave tab → **Adjust Balance**           | `POST /leaves/ledger { employeeId, leaveTypeId, entryDate, days, reason: 'opening' \| 'adjustment', remarks }`                                             | `leaves.balances.edit` (on that employee)     |

Please keep:

- `GET /leaves/balances` listing the types a person's policy covers even before any allotment
  (rows with `entitled: 0`, from `lv.fn_leave_coverage`). The profile uses those rows to say "No
  leave has been given to X for 2026 yet" and to read the current leave year (`fiscalYear`).
- The `fieldErrors` names of `POST /leaves/ledger` (`days`, `remarks`, `reason`, `leaveTypeId`,
  `entryDate`): the dialog shows each under its field.

## 3. How leave reaches a person (reference)

1. **Coverage, automatic.** An active company-level distribution policy covers everyone, new
   employees included, except people enrolled in an active employee-level policy of the same
   kind. With no active distribution policy, everyone gets every active type at its default.
2. **Days, from an allotment run.** Coverage gives no days. `lv.usp_leave_allotment_process`
   posts them. It is idempotent (a type already allotted for the year is skipped), so running it
   again for everyone or for one person is safe. It skips people who have left, types with Auto
   Allotment off (unless named), gender / marital status mismatches, and probation when the type
   does not allow it. Pro Rated types give joiners the months left in the year.
3. **By hand.** An opening balance (once per type and year) or an adjustment (+/−, reason
   required) through `POST /leaves/ledger`. The employee is notified.

Not built (a possible later request): nothing allots automatically when an employee is created
or enrolled. HR runs it from the profile, the Enroll dialog's checkbox or the Allotment dialog.
A nightly or on-create allotment for new joiners would remove that step.
